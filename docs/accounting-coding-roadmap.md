# نقشه راه کدینگ حسابداری (برنچ `coding`)

اگر کار قطع شد، از جدول وضعیت بفهمید کدام مرحله تمام شده و از **نقطه ادامه** همان مرحله شروع کنید.
مرحلهٔ بعد را شروع نکنید تا همهٔ تیک‌های «معیار اتمام» مرحلهٔ جاری خورده باشد.

سند فرانت (API و UI): [`docs/accounting-frontend.md`](accounting-frontend.md) — بعد از هر مرحله پر می‌شود.

وضعیت‌ها: `شروع‌نشده` | `در حال انجام` | `تمام`

| مرحله | عنوان | وضعیت | تاریخ |
|------|--------|--------|--------|
| ۱ | زیرساخت کدینگ | تمام | 2026-08-31 |
| ۲ | موتور سند دوطرفه | تمام | 2026-08-31 |

**معماری (عوض نشود مگر با تصمیم صریح)**
- جداول فعلی منبع عملیات می‌مانند: `purchases`, `expenses`, `invoices`, `shop_accounts`, `daily_shop_reconciliations`, …
- کدینگ و سند روی آن‌ها سوار می‌شود. POS، تطبیق روزانه و موجودی انبار را بازنویسی نکنید.
- واحد مبلغ: همان `decimal(15,2)` پروژه. اختلاف مجاز تراز سند: `0.01` تومان.
- هر فروشگاه (`atelier_id`) درخت حساب و شماره سند جدا دارد.

### ۲-۲. سرویس

`app/Services/AccountingVoucherService.php`

متدها:
- `post(atelierId, date, description, sourceType, sourceId, lines): Voucher`
- `reverse(voucher): Voucher` — برای هر آرتیکل، بدهکار و بستانکار جابه‌جا؛ `source_type` همان منبع با پسوند یا `reverses_voucher_id`
- `findPosted(sourceType, sourceId): ?Voucher`

کنترل‌ها قبل از insert:
1. مجموع debit و credit برابر باشند (تلرانس ۰.۰۱)
2. هیچ ردیفی هر دو ستون پر یا هر دو صفر نباشد
3. همه `account_id` مال همین `atelier_id` باشند
4. اگر سند `posted` برای این منبع هست، همان را برگردان (idempotent)
5. شماره سند: `MAX(number)+1` داخل تراکنش با قفل فروشگاه

ثبت فقط داخل `DB::transaction`.

### ۲-۳. کلید رویداد (برای مرحله ۳ و ۴)

| رویداد | source_type | source_id |

## مرحله ۳ — فروش، وصول، خزانه

**هدف:** پول فروش وارد دفتر شود. مسیر نقد: صندوق فروش → تطبیق → حساب ۱/۲. تراز آزمایشی روی سناریوی تست صفر باشد.

**عمداً نه:** فاکتور خرید، تولید، برگشت، حقوق، عوض کردن `FinancialReportController`.

### ۳-۱. اعداد فروش از کجا خوانده شود

از مدل فعلی `Purchase` (بازه را عوض نکنید؛ فقط پست کنید):

| مقدار | منبع |
|-------|------|
| فروش ناخالص خطوط | `remainingLineSalesTotal()` |
| تخفیف | `discount_amount` یا `ShopSalesReportService::discountGivenForPurchase` |
| اعتبار مصرف‌شده | `credit_used` |
| نقد | `cash_amount` |
| کارت | `card_amount` |
| چک | `chequeAmount()` |
| نسیه | `payment_type=debt` → مانده قابل پرداخت |
| اقساط | کل فاکتور طلب: درآمد روز فروش، صندوق = قسط اول نقد/کارت، باقی `11201`؛ پرداخت بعدی فقط د صندوق / ی دریافتنی |
| بها | `remainingLinePurchaseCost()` — برای تولید از `purchase_price` خط که از FIFO آمده |

ترکیب نقد+کارت+چک روی یک فاکتور مجاز است (`immediatePaidAmount` + چک).

## مرحله ۵ — گزارش دفتر کل

**هدف:** همهٔ اعداد این گزارش از `accounting_lines` بیاید. `ReportController` و `FinancialReportController` را حذف یا عوض نکنید.

### ۵-۱. سرویس و روت

- پیشوند روت: `accounting/...`

تاریخ ورودی شمسی مثل `FinancialReportController` (`Y-m-d` جلالی).

### ۵-۲. تراز آزمایشی

برای هر حساب دارای گردش در بازه (یا همهٔ معین/تفصیلی فعال):

- گردش بدهکار = SUM(debit)
- گردش بستانکار = SUM(credit)
- مانده = با توجه به `nature`: اگر debit-nature باشد `debit-credit` در ستون بدهکار مانده؛ اگر منفی در بستانکار.

سطر جمع کل: دو ستون مانده باید برابر باشند. اگر نبود، باگ مرحله ۲/۳/۴ است نه گزارش.

سطح گزارش MVP: تفصیلی + معین بدون تفصیلی. گروه را می‌توان جمع زد.

### ۵-۳. دفتر معین / تفصیلی

ورودی: یک `account_id`. خروجی لیست آرتیکل‌ها با تاریخ، شماره سند، شرح، بدهکار، بستانکار، ماندهٔ جاری.

مرتب‌سازی: `vouchers.date`, `vouchers.number`, `lines.sort_order`.  
سند `reversed` در گردش نیاید؛ سند storno به‌عنوان ردیف جدا بیاید.

### ۵-۴. سود و زیان

از مانده حساب‌های `kind=revenue` و `cogs` و `expense` در بازه (فقط گردش همان بازه، نه مانده انباشته):

```
درآمد فروش (411)
− برگشت و تخفیف (412)
− بهای تمام‌شده (511)
= سود ناخالص
− هزینه جاری (611) − حقوق (612) − اعتبار (613)
+ سایر درآمد (431)
= سود خالص دوره
```

از مرحله ۶ مبنای دفتر و گزارش POS هر دو تعهدی‌اند. فیلد `note` در API اختلاف جزئی تخفیف/زمان‌بندی را یادآوری می‌کند.

### ۵-۵. ترازنامه

نقطهٔ زمانی `as_of` (پایان روز):

- دارایی: مانده حساب‌های `kind=asset`
- بدهی: `liability`
- سرمایه: `equity` + سود خالص از اول تاریخچه تا `as_of` (یا تا وقتی بستن سال نداریم، سود دوره را زیر سرمایه نشان دهید با برچسب «سود جاری»)

معادله: دارایی = بدهی + سرمایه (+ سود جاری). اگر نخواند، سند نامتوازن یا سود دو بار در ترازنامه آمده.

### ۵-۶. تطبیق با نقد عملیاتی

جدول کمکی در پاسخ ترازنامه یا endpoint جدا:

| تفصیلی | مانده دفتر | مانده `ShopAccountBalanceService` |
|--------|-----------|-----------------------------------|
| حساب ۱ / ۲ / تنخواه | از دفتر | `balances()` |
| صندوق فروش | از دفتر | معادل عملیاتی ندارد؛ باید ≈ فروش نقد وصول‌نشده در تطبیق |

اگر حساب ۱ دفتر ≠ سرویس موجودی: اول واریز تطبیق و هزینه پرداخت‌شده را در سندها کم/زیاد کنید (مرحله ۳ و ۴)، گزارش را دستکاری نکنید.

## اگر وسط کار گیر کردید

1. جدول بالای فایل را به‌روز کنید.
2. از **نقطه ادامه همان مرحله** شروع کنید.
3. سند نامتوازن = باگ مرحله ۲ یا نگاشت ۳/۴؛ گزارش ۵ را دست نزنید.
4. مانده حساب فروشگاه ≠ دفتر = مسیر صندوق فروش → تطبیق (۳-۵) یا هزینه پرداخت‌نشده که از نقد کم شده.
5. سود دفتر ≠ گزارش POS = بعد از ۶-الف/ب/ج باید نزدیک باشند (تخفیف و زمان‌بندی).
