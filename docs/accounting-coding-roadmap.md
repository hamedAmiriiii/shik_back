# نقشه راه کدینگ حسابداری (برنچ `coding`)

اگر کار قطع شد، از جدول وضعیت بفهمید کدام مرحله تمام شده و از **نقطه ادامه** همان مرحله شروع کنید.
مرحلهٔ بعد را شروع نکنید تا همهٔ تیک‌های «معیار اتمام» مرحلهٔ جاری خورده باشد.

سند فرانت (API و UI): [`docs/accounting-frontend.md`](accounting-frontend.md) — بعد از هر مرحله پر می‌شود.

وضعیت‌ها: `شروع‌نشده` | `در حال انجام` | `تمام`

**معماری (عوض نشود مگر با تصمیم صریح)**
- جداول فعلی منبع عملیات می‌مانند: `purchases`, `expenses`, `invoices`, `shop_accounts`, `daily_shop_reconciliations`, …

| ستون | توضیح |

### ۲-۲. سرویس

`app/Services/AccountingVoucherService.php`

متدها:
- `post(atelierId, date, description, sourceType, sourceId, lines): Voucher`
- `reverse(voucher): Voucher` — برای هر آرتیکل، بدهکار و بستانکار جابه‌جا؛ `source_type` همان منبع با پسوند یا `reverses_voucher_id`
- `findPosted(sourceType, sourceId): ?Voucher`

کنترل‌ها قبل از insert:
1. مجموع debit و credit برابر باشند (تلرانس ۰.۰۱)
2. هیچ ردیفی هر دو ستون پر یا هر دو صفر نباشد
3. همه `account_id` مال همین `atelier_id` باشند
4. اگر سند `posted` برای این منبع هست، همان را برگردان (idempotent)
5. شماره سند: `MAX(number)+1` داخل تراکنش با قفل فروشگاه

ثبت فقط داخل `DB::transaction`.

### ۲-۳. کلید رویداد (برای مرحله ۳ و ۴)

قالب: `source_type` + `source_id`. نمونه:

| رویداد | source_type | source_id |
|--------|-------------|-----------|
| صدور فاکتور فروش | `purchase` | `purchases.id` |
| پرداخت یک قسط | `installment_pay` | `installments.id` |
| تسویه نسیه | `debt_settle` | `purchases.id` |

## مرحله ۳ — فروش، وصول، خزانه

**هدف:** پول فروش وارد دفتر شود. مسیر نقد: صندوق فروش → تطبیق → حساب ۱/۲. تراز آزمایشی روی سناریوی تست صفر باشد.

**عمداً نه:** فاکتور خرید، تولید، برگشت، حقوق، عوض کردن `FinancialReportController`.

### ۳-۱. اعداد فروش از کجا خوانده شود

از مدل فعلی `Purchase` (بازه را عوض نکنید؛ فقط پست کنید):

| مقدار | منبع |
|-------|------|
| فروش ناخالص خطوط | `remainingLineSalesTotal()` |
| تخفیف | `discount_amount` یا `ShopSalesReportService::discountGivenForPurchase` |
| اعتبار مصرف‌شده | `credit_used` |
| نقد | `cash_amount` |
| کارت | `card_amount` |
| چک | `chequeAmount()` |
| نسیه | `payment_type=debt` → مانده قابل پرداخت |
| اقساط | کل فاکتور طلب: درآمد روز فروش، صندوق = قسط اول نقد/کارت، باقی `11201`؛ پرداخت بعدی فقط د صندوق / ی دریافتنی |
| بها | `remainingLinePurchaseCost()` — برای تولید از `purchase_price` خط که از FIFO آمده |

ترکیب نقد+کارت+چک روی یک فاکتور مجاز است (`immediatePaidAmount` + چک).

### ۳-۲. چهار ورودی فروش — همه باید یک تابع مشترک را صدا بزنند

### ۵-۲. تراز آزمایشی

برای هر حساب دارای گردش در بازه (یا همهٔ معین/تفصیلی فعال):

- گردش بدهکار = SUM(debit)
- گردش بستانکار = SUM(credit)
- مانده = با توجه به `nature`: اگر debit-nature باشد `debit-credit` در ستون بدهکار مانده؛ اگر منفی در بستانکار.

سطر جمع کل: دو ستون مانده باید برابر باشند. اگر نبود، باگ مرحله ۲/۳/۴ است نه گزارش.

سطح گزارش MVP: تفصیلی + معین بدون تفصیلی. گروه را می‌توان جمع زد.

### ۵-۳. دفتر معین / تفصیلی

ورودی: یک `account_id`. خروجی لیست آرتیکل‌ها با تاریخ، شماره سند، شرح، بدهکار، بستانکار، ماندهٔ جاری.

مرتب‌سازی: `vouchers.date`, `vouchers.number`, `lines.sort_order`.  
اصل `reversed` و سند storno هر دو در گردش می‌آیند تا مانده خنثی شود. `scopePosted` فقط سند فعال (غیربرگشتی) است، نه گردش دفتر.

### ۵-۴. سود و زیان

از مانده حساب‌های `kind=revenue` و `cogs` و `expense` در بازه (فقط گردش همان بازه، نه مانده انباشته):

```
درآمد فروش (411)
− برگشت و تخفیف (412)
− بهای تمام‌شده (511)
= سود ناخالص
− هزینه جاری (611) − حقوق (612) − اعتبار (613)
+ سایر درآمد (431)
= سود خالص دوره
```

از مرحله ۶ مبنای دفتر و گزارش POS هر دو تعهدی‌اند. فیلد `note` در API اختلاف جزئی تخفیف/زمان‌بندی را یادآوری می‌کند.

### ۵-۵. ترازنامه

نقطهٔ زمانی `as_of` (پایان روز):

- دارایی: مانده حساب‌های `kind=asset`
- بدهی: `liability`
- سرمایه: `equity` + سود خالص از اول تاریخچه تا `as_of` (یا تا وقتی بستن سال نداریم، سود دوره را زیر سرمایه نشان دهید با برچسب «سود جاری»)

معادله: دارایی = بدهی + سرمایه (+ سود جاری). اگر نخواند، سند نامتوازن یا سود دو بار در ترازنامه آمده.

### ۵-۶. تطبیق با نقد عملیاتی

جدول کمکی در پاسخ ترازنامه یا endpoint جدا:

| تفصیلی | مانده دفتر | مانده `ShopAccountBalanceService` |
|--------|-----------|-----------------------------------|
| حساب ۱ / ۲ / تنخواه | از دفتر | `balances()` |
| صندوق فروش | از دفتر | معادل عملیاتی ندارد؛ باید ≈ فروش نقد وصول‌نشده در تطبیق |

اگر حساب ۱ دفتر ≠ سرویس موجودی: اول واریز تطبیق و هزینه پرداخت‌شده را در سندها کم/زیاد کنید (مرحله ۳ و ۴)، گزارش را دستکاری نکنید.

- بستن سال و سود انباشته واقعی → مرحله ۷
- تفصیلی به‌ازای مشتری/ذی‌نفع → مرحله ۸
- مالیات / ارزش افزوده → مرحله ۹
- استهلاک و لات FIFO کالای کاتالوگ و حذف گزارش مالی فعلی — هنوز خارج از این سه مرحله

### معیار اتمام مرحله ۶

- [x] اقساط و چک در دفتر تعهدی‌اند
- [x] اعتبار دو بار در سود دفتر نیست
- [x] پرمیشن `accounting` هست
- [x] فروشگاه جدید درخت حساب دارد
- [x] بکاپ جداول دفتر را شامل است
- [x] افتتاحیه یا سیاست «از امروز» مکتوب و اجرا شده
- [x] تست ۶-ز سبز است (`php artisan accounting:health-check {atelier_id}`؛ سناریوی هشت‌مرحله‌ای دستی روی فروشگاه خالی)

### نقطه ادامه مرحله ۶

تمام. مرحلهٔ بعد: ۷ بستن سال. شروع نکنید تا روز کار مشخص شود.

## مرحله ۷ — بستن سال و سود انباشته

**هدف:** پایان سال شمسی، ماندهٔ درآمد/هزینه/بها صفر شود و سود (یا زیان) به `35` سود انباشته برود. ترازنامه دیگر «سود جاری» سال بسته‌شده را جدا نگذارد.

سال مالی = سال شمسی همان فروشگاه (۱ فروردین تا آخر اسفند). تاریخ سند در DB میلادی می‌ماند؛ ورودی API شمسی `Y-m-d`.

معماری مرحله ۱–۶ عوض نشود: POS منبع عملیات است؛ فقط سند بستن سال اضافه می‌شود.

### ۷-الف. قفل دوره و کلید سند

- `source_type=year_close` ، `source_id` = سال شمسی (مثلاً `1404`) — یک‌بار برای هر فروشگاه، idempotent مثل بقیهٔ پوسترها
- جدول جدا لازم نیست مگر بخواهید وضعیت سال (`open` / `closed`) را جدا از سند نگه دارید؛ MVP: وجود سند `posted` غیربرگشتی یعنی آن سال بسته است
- `AccountingVoucherService::post` اگر تاریخ سند داخل سال بسته‌شده باشد رد کند (۴۲۲)، به‌جز خود سند بستن و storno بازگشایی
- صندوق و فروش روز بعد از ۲۹/۳۰ اسفند روی سال بعد می‌روند

فایل‌ها: `AccountingVoucher` ثابت `SOURCE_YEAR_CLOSE`، سرویس جدید مثلاً `AccountingYearCloseService`، هوک در `post` برای قفل تاریخ.

### ۷-ب. آرتیکل بستن

از `AccountingReportService::profitLoss` برای همان سال (از ۱ فروردین تا آخر اسفند):

| حساب | بدهکار | بستانکار |
|------|--------:|--------:|
| `411` درآمد فروش | مانده بستانکار | |
| `431` سایر درآمد | مانده بستانکار | |
| `35` سود انباشته | | جمع درآمدها |
| `35` سود انباشته | مانده بدهکار `412`+`511`+`611`+`612`+`613` | |
| `412` تخفیف | | مانده بدهکار |
| `511` بها | | مانده بدهکار |
| `611` / `612` / `613` | | مانده بدهکار |

اگر زیان باشد، خالص `35` بدهکار می‌شود. سند نامتوازن نشود (تلرانس ۰٫۰۱). اگر تراز آزمایشی سال نامتوازن است، بستن را رد کنید.

کد `35` در بذر مرحله ۱ هست؛ ثابت `CODE_RETAINED='35'` به `ChartOfAccountsSeeder` اضافه شود.

تاریخ سند = آخرین روز اسفند همان سال (میلادی در DB).

### ۷-ج. گزارش بعد از بستن

`balanceSheet`: «سود جاری» فقط از **روز بعد از آخرین سال بسته‌شده** تا `as_of` است. سود سال‌های بسته‌شده داخل ماندهٔ `35` است؛ دوباره جمع نشود.

`profit-loss?from=&to=`: گردش همان بازه می‌ماند (برای دیدن سال بسته‌شده هم لازم است). بعد از بستن، اگر `from`/`to` داخل سال بعد باشد، درآمد/هزینه سال قبل صفر است.

فرانت: `POST /api/accounting/year-close` با `{ "year": 1404 }` (staff). لیست سال‌های بسته‌شده از `GET /api/accounting/vouchers?source_type=year_close`. دکمه را فقط صاحب/حسابداری ببیند. بازگشایی در MVP لازم نیست؛ اگر خواستید storno همان سند + برداشتن قفل.

بکاپ: `source_type=year_close` جدول عملیاتی ندارد؛ در `ShopBackupTables::voucherSourceTables` نیاید (مثل `opening` / `manual`).

### ۷-د. عمداً نه

- بستن میان‌دوره / اصلاحیه بعد از اظهارنامه
- تقسیم سود بین شرکا
- سند افتتاحیه سال بعد جدا از گردش دارایی (مانده BS خودش حمل می‌شود)

### معیار اتمام مرحله ۷

- [ ] سند بستن سال متوازن و تکرارناپذیر است
- [ ] ثبت رویداد در سال بسته‌شده رد می‌شود
- [ ] ترازنامه سود سال بسته‌شده را دو بار نشان نمی‌دهد
- [ ] `35` در بذر و گزارش سرمایه آمده
- [ ] سند فرانت به‌روز شده

### نقطه ادامه مرحله ۷

1. ۷-الف قفل و کلید → ۲. ۷-ب آرتیکل → ۳. ۷-ج گزارش و API → ۴. فرانت و تست یک فروشگاه روی سال شمسی تمام‌شده (یا سال آزمایشی).

## مرحله ۸ — تفصیلی طرف‌حساب

**هدف:** طلب و بدهی به‌ازای شخص باشد، نه یک معین/تفصیلی عمومی. عرف ایران: زیر معین دریافتنی/پرداختنی، هر طرف‌حساب یک تفصیلی.

کدهای قفل‌شدهٔ `11201` و `21101` **عوض نشوند**. همان «عمومی / بدون شخص» می‌مانند (مشتری بی‌تلفن، هزینه بدون ذی‌نفع).

### ۸-الف. بذر و لینک

زیر `112` و `211` تفصیلی جدید بسازید (کد بعدی آزاد، مثلاً `11202` به‌بعد و `21102` به‌بعد). قالب:

- `linked_type=user_shiksho` ، `linked_id=user_shiksho.id` — مشتری فروش (`purchases.phone` → همان ردیف) و ذی‌نفع فاکتور/هزینه (`beneficiary_id`)
- یک نفر هم مشتری است هم تأمین‌کننده: **دو تفصیلی** (طلب `112xx` و بدهی `211xx`) درست است
- نام تفصیلی = نام شخص؛ با عوض شدن نام `user_shiksho` همگام شود (مثل نام حساب فروشگاه)

`ChartOfAccountsSeeder` / `AccountingLedger`: `partyArAccountId($atelierId, $userShikshoId)` و `partyApAccountId(...)`. اگر شخص نبود → همان `11201` / `21101`.

ساخت شخص جدید (`CustomerController` / ذی‌نفع) همان لحظه تفصیلی بسازد؛ idempotent.

### ۸-ب. پوسترها

| رویداد | امروز | بعد از ۸ |
|--------|--------|----------|
| فروش نسیه / اقساط / اعتبار دستی | `11201` | تفصیلی همان مشتری اگر تلفن/user_shiksho دارد |
| وصول قسط / تسویه نسیه | یِ `11201` | همان تفصیلی فروش |
| فاکتور/هزینه نسیه | `21101` | تفصیلی ذی‌نفع اگر `beneficiary_id` پر است |
| تسویه `document_payment` | دِ `21101` | همان تفصیلی سند |

چک و صندوق عوض نشود. ماندهٔ تاریخی روی `11201`/`21101` را در MVP جابه‌جا نکنید (مثل سیاست «از امروز به بعد»).

### ۸-ج. گزارش و بکاپ

دفتر معین همان API مرحله ۵ است؛ فرانت درخت را با تفصیلی‌های شخص نشان بدهد. فیلتر «طرف‌حساب» لازم نیست اگر `account_id` انتخاب می‌شود.

`ShopBackupTables`: `typed_fks` برای `linked_id` وقتی `linked_type=user_shiksho` → جدول `user_shiksho`. سند و خط بعد از `user_shiksho` در تعریف بکاپ هستند؛ ترتیب درج را چک کنید (تفصیلی حساب قبل از اسناد است — `linked_id` شخص باید بعد از restore `user_shiksho` remap شود). الان `accounting_accounts` قبل از `user_shiksho` درج می‌شود؛ در ۸ یا `linked_id` را در `updateForeignKeys` بعد از همهٔ جداول remap کنید یا تعریف `accounting_accounts` را بعد از `user_shiksho` بیاورید **بدون** شکستن FK والد درخت. ترجیح: remap دوم در `updateForeignKeys` (idMap شخص آماده است حتی اگر حساب زودتر درج شده؛ `linked_id` در پاس دوم درست می‌شود اگر `user_shiksho` قبل از پاس دوم insert شده باشد). پس در مرحله ۸ ترتیب تعریف را طوری کنید که `user_shiksho` **قبل از** پاس نهایی FK حساب‌ها در maps باشد — یعنی `user_shiksho` قبل از `updateForeignKeys` insert شود (الان همین است). فقط `typed_fks` را گسترش دهید.

### ۸-د. عمداً نه

- تفصیلی جدا برای هر فاکتور
- تفصیلی پرسنل حقوق (همان `612` کافی است)
- ادغام طلب و بدهی یک نفر در یک حساب

### معیار اتمام مرحله ۸

- [ ] فروش با تلفن روی تفصیلی همان مشتری است نه فقط `11201`
- [ ] فاکتور با ذی‌نفع روی تفصیلی همان نفر است نه فقط `21101`
- [ ] بدون شخص، عمومی باقی می‌ماند
- [ ] بکاپ `linked_id` شخص را remap می‌کند
- [ ] سند فرانت به‌روز شده

### نقطه ادامه مرحله ۸

1. ۸-الف بذر/لینک → ۲. ۸-ب پوستر فروش و اسناد → ۳. بکاپ typed_fks → ۴. تست یک مشتری با دو فروش نسیه و یک فاکتور.

## مرحله ۹ — مالیات ارزش افزوده

**هدف:** روی فروش و خرید مشمول، مالیات از مبلغ جدا شود و به حساب بدهی/دارایی مالیاتی برود. اظهارنامه و ارسال به سامانه در این مرحله نیست.

نرخ را در کد قفل نکنید: `Setting` فروشگاه (مثلاً `vat_enabled` و `vat_rate` درصد). پیش‌فرض خاموش تا فروشگاه‌های فعلی خراب نشوند.

### ۹-الف. حساب‌ها (قفل بعد از شروع کار)

به بذر اضافه شود:

| کد | سطح | نام | ماهیت | kind |
|----|------|------|--------|------|
| `115` | معین | مالیات دریافتنی | بدهکار | asset |
| `11501` | تفصیلی | ارزش افزوده خرید | بدهکار | asset |
| `213` | معین | مالیات پرداختنی | بستانکار | liability |
| `21301` | تفصیلی | ارزش افزوده فروش | بستانکار | liability |

ثابت‌ها: `CODE_VAT_INPUT='11501'` ، `CODE_VAT_OUTPUT='21301'`.

### ۹-ب. محاسبه

MVP: قیمت‌های فعلی **با مالیات** فرض شوند مگر خلافش در تنظیمات باشد.

`vat = round(gross * rate / (100 + rate), 2)`  
`net = gross - vat`

اگر `vat_enabled` خاموش است، پوسترها مثل امروز بمانند.

| رویداد | آرتیکل اضافه |
|--------|----------------|
| فروش مشمول | یِ `411` = خالص ؛ یِ `21301` = مالیات ؛ بدهکارها (صندوق/طلب/چک/تخفیف/اعتبار) همان مبلغ ناخالص فاکتور |
| برگشت فروش | برعکس همان مالیات خروجی |
| فاکتور خرید مشمول | دِ موجودی = خالص ؛ دِ `11501` = مالیات ؛ بستانکار نقد/چک/`211xx` = ناخالص |
| هزینه جاری مشمول | دِ `611` خالص + دِ `11501` مالیات (اگر پرچم روی هزینه باشد) |
| حقوق، تطبیق، تنخواه، افتتاحیه، بستن سال | مالیات ندارد |

کدام فاکتور/فروش مشمول است: تنظیم سراسری فروشگاه در MVP کافی است. پرچم روی هر فاکتور اختیاری مرحلهٔ بعد.

### ۹-ج. گزارش

در `profit-loss` درآمد `411` خالص است (مالیات فروش درآمد نیست). در ترازنامه `11501` دارایی و `21301` بدهی.

API کمکی اختیاری: `GET /api/accounting/vat-summary?from=&to=` با `output` (گردش بستانکار `21301`)، `input` (گردش بدهکار `11501`)، `payable = output - input`. اظهارنامه نسازید.

فرانت: کلید تنظیمات نرخ؛ در فاکتور فروش/خرید ستون مالیات اگر فعال باشد.

بکاپ: حساب‌های جدید داخل `accounting_accounts` هستند؛ تنظیم نرخ داخل `settings`.

### ۹-د. عمداً نه

- مالیات بر درآمد / تکلیفی / حقوق
- صورت معاملات فصلی و سامانه مودیان
- چند نرخ همزمان روی یک فاکتور (مگر بعداً روی قلم)

### معیار اتمام مرحله ۹

- [ ] با مالیات خاموش هیچ آرتیکل `11501`/`21301` نیست
- [ ] با مالیات روشن، فروش ناخالص = خالص + خروجی و سند متوازن است
- [ ] سود دفتر مالیات فروش را درآمد نمی‌شمارد
- [ ] سند فرانت تنظیمات و در صورت وجود vat-summary را دارد

### نقطه ادامه مرحله ۹

1. ۹-الف بذر → ۲. تنظیمات نرخ → ۳. پوستر فروش/خرید → ۴. گزارش و تست یک فاکتور فروش و یک خرید.

### عمداً بعد از ۹ هنوز نه

- استهلاک
- لات FIFO کالای کاتالوگ
- حذف `GET /api/financial-report/monthly`
- بازسازی تاریخچهٔ اسناد قبل از فعال‌سازی

## اگر وسط کار گیر کردید

1. جدول بالای فایل را به‌روز کنید.
2. از **نقطه ادامه همان مرحله** شروع کنید.
3. سند نامتوازن = باگ مرحله ۲ یا نگاشت ۳/۴/۷/۸/۹؛ گزارش ۵ را دست نزنید مگر معیار همان مرحله بگوید.
4. مانده حساب فروشگاه ≠ دفتر = مسیر صندوق فروش → تطبیق (۳-۵) یا هزینه پرداخت‌نشده که از نقد کم شده.
5. سود دفتر ≠ گزارش POS = بعد از ۶ باید نزدیک باشند؛ بعد از ۹ درآمد دفتر خالص از مالیات است و POS اگر ناخالص نشان بدهد فرق عادی است.
6. بستن سال: ترازنامه سود را دو بار نشان داد = `current_profit` هنوز سال بسته‌شده را جمع می‌کند (۷-ج).
7. همهٔ طلب‌ها روی `11201` ماند = شخص لینک نشده یا پوستر مرحله ۸ وصل نیست.
