# طرح فنی اتصال به سامانه مؤدیان

**هدف:** فروش‌های فروشگاه به‌صورت صورتحساب الکترونیکی صادر و به سامانه مؤدیان ارسال شود؛ وضعیت پیگیری شود؛ مرجوعی، حذف و ویرایش فاکتور به صورتحساب برگشتی، ابطالی و اصلاحی تبدیل شوند؛ و نسخهٔ ارسال‌شده بدون تغییر نگه داشته شود.

**وضعیت:** طراحی — هنوز کدی نوشته نشده.

---

## ۰. منابع و نسخه‌ها

| سند | نسخه | کاربرد |
|-----|------|--------|
| دستورالعمل فنی نحوه اتصال به سامانه مؤدیان | به‌روزرسانی ۱۴۰۵/۰۵/۱۱ | API، امضا، رمزنگاری، استعلام |
| دستورالعمل صدور صورتحساب الکترونیکی `RC_IITP.IS_V7.9` | تیر ۱۴۰۵ | فیلدها، الگوها، قواعد اصلاحی/ابطالی/برگشت، ماده ۹ |

این طرح از روی بازنشر این اسناد نوشته شده. **قبل از شروع هر مرحله، PDF رسمی از `intamedia.ir` گرفته و جدول فیلدها و کدهای خطا از آن برداشته شود.** هرجا در این سند «طبق سند» آمده، عدد یا کد را از حافظه ننویسید.

خلاصهٔ فنی سامانه:

- آدرس پایه: `https://tp.tax.gov.ir/req/api/` — محیط تست: `https://sandboxrc.tax.gov.ir/req/api/`
- `self-tsp/...` برای مؤدی که خودش می‌فرستد؛ `tsp/...` برای شرکت معتمد.
- ارسال **غیرهمگام**: `async/normal-enqueue` و `async/fast-enqueue`. استعلام و اطلاعات **همگام**: `sync/...`
- متدهای همگام: `GET_TOKEN`، `GET_SERVER_INFORMATION` (کلید عمومی سازمان)، `GET_FISCAL_INFORMATION`، `INQUIRY_BY_UID`، `INQUIRY_BY_REFERENCE_NUMBER`، `INQUIRY_BY_TIME`، `INQUIRY_BY_TIME_RANGE`، `GET_SERVICE_STUFF_LIST`، `GET_ECONOMIC_CODE_INFORMATION`.
- وضعیت بسته: `PENDING` → `SUCCESS` یا `FAILED` (+ فهرست خطا و هشدار).
- امنیت: JSON نرمال‌سازی → امضای `RSA-2048/SHA256` با کلید خصوصی مؤدی → رمز `AES-256-GCM` با کلید تصادفی → رمز کلید تصادفی با `RSA-OAEP-SHA256` و کلید عمومی سازمان.
- مبالغ به **ریال**؛ محاسبات **قطع** (truncate) می‌شوند، گرد کردن ممنوع.

## ۱. تصمیم‌ها

| موضوع | تصمیم | پیامد در طراحی |
|-------|-------|-----------------|
| روش اتصال | **باز** (مستقیم یا شرکت معتمد) | لایهٔ `MoadianGateway` با دو پیاده‌سازی؛ بقیهٔ سیستم فقط با این لایه کار می‌کند |
| قیمت و مالیات | **برای هر فروشگاه قابل انتخاب** (`price_includes_vat`) | ماشین‌حساب مالیات دو حالت دارد؛ در حالت «بدون مالیات» جمع صندوق تغییر نمی‌کند و مالیات فقط در صورتحساب مؤدیان اضافه می‌شود |
| اعتبار باشگاه (`credit_used`) | **تخفیف** | تخفیف صورتحساب = `discount_amount` (غیر اقساطی) + `credit_used`؛ به نسبت مبلغ بین ردیف‌ها پخش می‌شود و پایهٔ مالیات را کم می‌کند |
| اختلال در روند فعلی | **ممنوع** | هیچ کد فروش/برگشت/حذف تغییر نکرده؛ جمع‌آورنده (`moadian:run`) در پس‌زمینه فروش‌ها را فقط می‌خواند |

### تصمیم‌های باز دیگر (قبل از مرحلهٔ مربوط بسته شوند)

1. **شرکت معتمد**: اگر این راه انتخاب شد، کدام شرکت؛ API هر شرکت متفاوت است.
3. **مهلت ارسال** (ماده ۹): عدد روز از سازمان اعلام می‌شود؛ در تنظیمات سراسری نگه داشته شود، در کد قفل نشود.
4. **کد واحد اندازه‌گیری** برای `piece|kg|meter` طبق جدول سند.

## ۳. معماری

```
ورودی‌های فروش / مرجوعی / حذف / ویرایش
            │  (بعد از commit)
            ▼
   MoadianDocumentService      ← تصمیم: اصلی / اصلاحی / ابطالی / برگشت؟ ساخت سند محلی
            │
            ├── MoadianTaxCalculator     ← مالیات و عوارض هر ردیف (مشترک با حسابداری)
            ├── MoadianInvoiceBuilder    ← JSON طبق v7.9 (ریال، truncate، taxid)
            ├── MoadianTaxIdGenerator    ← شمارهٔ ۲۲ رقمی + سریال
            └── MoadianValidator         ← اعتبارسنجی محلی قبل از ارسال
            ▼
   moadian_documents (+ items)   ← نسخهٔ غیرقابل‌تغییر
            ▼
   moadian:send  (زمان‌بندی)  →  MoadianGateway  →  SelfTspGateway | TspProviderGateway
   moadian:inquire (زمان‌بندی) →  MoadianGateway  →  به‌روزرسانی وضعیت
```

اصول:

- **فروش هرگز منتظر مؤدیان نمی‌ماند.** فروش ثبت می‌شود؛ سند مؤدیان در صف محلی می‌رود.
- **کد فروش فعلی تا حد ممکن دست نمی‌خورد.** فقط یک قلاب بعد از هر عملیات.
- **هر چیزی که ارسال شد، دیگر ویرایش نمی‌شود.** تغییر = سند جدید.
- **سند محلیِ هنوز ارسال‌نشده را می‌شود بازسازی کرد** (مثلاً فروش ۵ دقیقه بعد ویرایش شد و هنوز نرفته بود ← همان سند اصلی بازسازی می‌شود، نیازی به اصلاحی نیست).

### ۳-۱. `MoadianGateway`

```php
interface MoadianGateway
{
    public function fiscalInformation(MoadianShopSetting $s): array;
    /** @param MoadianDocument[] $docs  @return array<uid, referenceNumber|null> */
    public function send(MoadianShopSetting $s, array $docs): array;
    /** @return InquiryResult[] */
    public function inquireByReference(MoadianShopSetting $s, array $referenceNumbers): array;
    public function stuffList(MoadianShopSetting $s, int $page): array;
}
```

- `SelfTspGateway`: توکن، کلید عمومی سازمان، امضا و رمزنگاری با کلید فروشگاه. کتابخانهٔ `deriszadeh/moadian-php-sdk` بررسی شود (وب‌سرویس نسخهٔ ۲، phpseclib)؛ اگر فیلدهای v7.9 را پشتیبانی نکند، فقط لایهٔ رمزنگاری آن استفاده شود و JSON را خودمان بسازیم.
- `TspProviderGateway`: JSON ساده (بدون امضا) به API شرکت معتمد؛ نگاشت وضعیت‌های آن‌ها به وضعیت‌های ما.
- انتخاب با `moadian_shop_settings.connection_mode`.

## ۵. محاسبهٔ مالیات و عوارض

یک کلاس: `MoadianTaxCalculator`. حسابداری مرحلهٔ ۹ هم از همین استفاده کند؛ فرمول `round(gross*rate/(100+rate),2)` در نقشهٔ حسابداری با این جایگزین شود.

قواعد:

1. نرخ برای **هر ردیف** از `sstid` (کش `moadian_stuff_ids`)؛ نه یک نرخ برای کل فروشگاه.
2. همهٔ مبالغ به ریال: `ریال = تومان × ۱۰`.
3. هر مقدار محاسبه‌ای **truncate** به تعداد اعشار سند.
4. تخفیف فاکتور (`discount_amount`) به نسبت مبلغ روی ردیف‌ها پخش شود؛ باقی‌ماندهٔ truncate روی آخرین ردیف.
5. عوارض/سایر مالیات فقط اگر برای آن `sstid` تعریف شده؛ وگرنه صفر.

### حالت «قیمت شامل مالیات» (`price_includes_vat = true`)

مبلغ پرداختی مشتری ثابت است و مالیات از داخل آن جدا می‌شود:

```
gross = مبلغ ردیف بعد از تخفیف (ریال)
adis  = truncate(gross × 100 / (100 + rate))
vam   = truncate(adis × rate / 100)
```

`adis + vam` ممکن است چند ریال با `gross` فرق کند. سامانه `vam` را از روی `adis` کنترل می‌کند، پس این اختلاف پذیرفته و در سند ثبت می‌شود (`rounding_diff`). روی sandbox با چند نرخ و مبلغ تست شود.

صندوق فروش تغییری نمی‌کند.

### حالت «قیمت بدون مالیات» (`price_includes_vat = false`)

```
adis = مبلغ ردیف بعد از تخفیف
vam  = truncate(adis × rate / 100)
مبلغ قابل پرداخت = Σ(adis + vam + odam)
```

**اثر روی صندوق:** جمع سبد، مبلغ قابل پرداخت، رسید، پیش‌فاکتور و حسابداری باید ردیف «مالیات» داشته باشند. این بزرگ‌ترین تغییر فرانت است و فقط برای فروشگاه‌هایی که این حالت را انتخاب کنند فعال می‌شود.

## ۶. چرخهٔ عمر سند

### ۶-۱. نگاشت عملیات فعلی به سند مؤدیان

| عملیات فعلی | کد | سند مؤدیان |
|--------------|-----|-------------|
| فروش جدید (همهٔ ورودی‌ها) | قلاب بعد از commit | اصلی (`ins=1`) |
| مرجوعی جزئی | `PurchaseItemReturnService::returnItem` | برگشت از فروش (`ins=4`) روی آخرین سند پذیرفته‌شده؛ فقط کاهش تعداد، قیمت واحد و نرخ ثابت |
| مرجوعی‌ای که همهٔ اقلام را صفر کند | همان | ابطالی (`ins=3`) — سامانه برگشت ۱۰۰٪ را نمی‌پذیرد |
| مرجوعی کامل | `returnPurchase` | ابطالی |
| حذف فاکتور | `PurchasedProductController@destroy` | ابطالی؛ حذف فاکتور ادامه پیدا می‌کند، سند و ردیف‌هایش می‌مانند |
| تغییر شماره تلفن | `update` | نوع ۲: بی‌اثر. نوع ۱ (خریدار عوض شد): ابطالی + اصلی جدید |
| تغییر مبلغ/اعتبار | `update` | اصلاحی (`ins=2`) |
| بازنویسی کامل | `store` با `replace_purchase_id` | همان اقلام و همان خریدار: اصلاحی. کالای جدید، خریدار جدید یا حذف قلم: ابطالی + اصلی جدید |

قواعد سامانه که `MoadianDocumentService` باید قبل از ساخت سند چک کند:

- روی هر سند فقط **یک** ابطالی؛ ابطالی هرگز مرجع نمی‌شود.
- اصلاحی: خریدار، `sstid`، نوع، الگو و نرخ عوض نمی‌شود؛ قلم جدید اضافه نمی‌شود.
- اصلاحی/برگشت روی سندی که هنوز پذیرفته نشده یا سند فعال دیگری رویش هست ← صبر (وابستگی).
- اگر سند مرجع هنوز **ارسال نشده**: سند جدید ساخته نمی‌شود؛ خود سند مرجع بازسازی می‌شود. اگر در همین حالت ابطال شد، سند محلی `discarded` می‌شود (سریال مصرف‌شده برنمی‌گردد).

### ۶-۲. وضعیت‌ها

```
draft ──► queued ──► sent(PENDING) ──► success
  │          │             │
  │          │             └──► failed ──► (اصلاح داده) ──► queued
  │          └──► blocked   (منتظر سند مرجع)
  └──► discarded            (ارسال‌نشده و دیگر لازم نیست)
```

- `blocked` ← وقتی سند مرجع `success` شد، خودکار `queued`.
- ارسال مجدد سند `failed`: آیا همان `taxid` قابل استفاده است یا سریال جدید لازم است، روی sandbox بررسی و این بند به‌روز شود.
- برای صورتحساب نوع ۱، واکنش خریدار (تأیید/رد در کارپوشه) روی مجاز بودن اصلاحی اثر دارد؛ راه استعلام آن از API در سند رسمی بررسی شود.

### ۶-۳. ارسال با تأخیر (ماده ۹)

اگر `now - indatim` > مهلت سراسری ← `insr = 1` و `indati2m = now` (میلی‌ثانیه). فروش‌های آفلاین (`client_id`) که دیر همگام می‌شوند معمولاً به این می‌خورند؛ `indatim` همیشه زمان واقعی فروش است.

## ۷. ارسال و استعلام

دستورها در `app/Console/Kernel.php`:

| دستور | زمان | کار |
|-------|------|-----|
| `moadian:send --limit=50` | هر دقیقه، `withoutOverlapping` | سندهای `queued` با `next_attempt_at` گذشته، گروهی برای هر فروشگاه |
| `moadian:inquire --limit=200` | هر ۵ دقیقه | `sent` ها با `INQUIRY_BY_REFERENCE_NUMBER` |
| `moadian:sync-stuff` | روزانه | به‌روزرسانی `moadian_stuff_ids` |
| `moadian:prune-logs` | روزانه | پاک‌سازی `moadian_api_logs` |

- توکن هر `memory_id` تا `expiresIn` کش شود؛ کلید عمومی سازمان هم کش شود.
- یک فروشگاه خراب (کلید اشتباه) نباید ارسال بقیه را متوقف کند: خطا برای همان فروشگاه ← `paused_reason`.
- استعلام دیرکرد: اگر سندی بیش از X ساعت `PENDING` ماند، `INQUIRY_BY_TIME_RANGE` برای پیدا کردن خطاهای بسته.

## ۸. مدیریت خطا

| دسته | نمونه | رفتار |
|------|-------|-------|
| موقت | قطعی شبکه، ۵xx، timeout، توکن منقضی | تکرار خودکار با فاصلهٔ افزایشی (۱، ۵، ۱۵، ۶۰ دقیقه…)؛ بعد از N بار ← `failed` |
| داده | `FAILED` با کد خطای اعتبارسنجی (نبود `sstid`، جمع اشتباه، کد اقتصادی نامعتبر) | `failed`؛ پیام فارسی به کاربر؛ بعد از اصلاح «ارسال مجدد» |
| پیکربندی | حافظهٔ غیرفعال، امضای نامعتبر، کلید ثبت‌نشده | توقف ارسال همان فروشگاه (`paused_reason`) + هشدار در پنل |
| منطقی (محلی) | اصلاحی روی سند ابطال‌شده، برگشت ۱۰۰٪ | قبل از ساخت سند جلوگیری شود؛ به ادمین نمایش داده شود |

- `MoadianValidator` قبل از ارسال: وجود `sstid` و نرخ برای همهٔ ردیف‌ها، کد اقتصادی فروشنده، اطلاعات خریدار برای نوع ۱، برابری جمع‌ها.
- جدول نگاشت کد خطای سامانه ← پیام فارسی از پیوست سند رسمی (`app/Support/Moadian/ErrorMessages.php`).
- هشدارها (`warnings`) ذخیره شوند ولی سند را `failed` نکنند.

## ۹. نگهداری اطلاعات ارسال‌شده

- `moadian_documents.payload` + `moadian_document_items` نسخهٔ قانونی و **غیرقابل‌تغییر** است. بعد از `sent` هیچ کدی این ستون‌ها را update نکند (در مدل با `saving` جلوگیری شود).
- حذف فاکتور، مرجوعی و بازنویسی روی این جدول‌ها اثر ندارد (`nullOnDelete`).
- بکاپ/بازیابی فروشگاه: این جدول‌ها داخل بکاپ فروشگاه باشند. بازیابی نباید سند ارسال‌شده را با نسخهٔ قدیمی جایگزین یا سریال را عقب ببرد.
- مدت نگهداری سندها طبق قانون؛ پاک‌سازی خودکار فقط برای `moadian_api_logs`.
- کلید خصوصی: رمزشده، فقط مالک فروشگاه یا ادمین سامانه تغییرش می‌دهد، هیچ API آن را برنمی‌گرداند.

## ۱۳. پیاده‌سازی انجام‌شده

به‌جای قلاب (hook) در کد فروش، یک **جمع‌آورنده** زمان‌بندی‌شده ساخته شد تا روند فعلی هیچ تغییری نکند:

- `moadian:run` هر دقیقه (`withoutOverlapping`) برای فروشگاه‌های `enabled`: جمع‌آوری ← ارسال ← استعلام. `moadian:prune-logs` روزانه فقط لاگ API را پاک می‌کند.
- فروش جدید: `purchases.id > start_purchase_id` (هنگام اولین فعال‌سازی = بیشترین شناسهٔ فعلی) و حداقل ۲ دقیقه از ثبت گذشته.
- فروش تغییرکرده: `purchases.updated_at` یا `purchased_products.updated_at` یا `purchase_item_returns.created_at` بعد از `moadian_sale_links.checked_at`. فروش حذف‌شده: لینک بدون خرید.
- کلید ردیف (`line_key`) = شناسهٔ کالا/تولیدی/مادهٔ اولیه + قیمت واحد (چون جایگزینی فاکتور ردیف‌ها را از نو می‌سازد).
- تصمیم (مقایسهٔ اثر انگشت و ردیف‌ها با آخرین سند ثبت‌شده): جدید ← اصلی؛ head ارسال‌نشده/ناموفق ← بازسازی همان سند؛ head در انتظار ← صبر؛ حذف یا برگشت کامل ← ابطالی؛ تغییر خریدار/نوع/شناسه/نرخ یا قلم جدید ← ابطالی + اصلی جدید؛ فقط کاهش ← برگشت از فروش؛ سایر ← اصلاحی. سند اصلاحی/برگشتی فقط بعد از `success` شدن مرجع ارسال می‌شود.
- API نسخه ۲: توکن = JWS(RS256) روی `{nonce, clientId}`؛ بستهٔ صورتحساب = JWE(RSA-OAEP-256 + A256GCM) روی JWS. چون OpenSSL در PHP فقط OAEP-SHA1 دارد، پدینگ OAEP-SHA256 دستی ساخته شده (`MoadianCrypto`).
- خطای پیکربندی (کلید/گواهی/حافظه/۴۰۱) فروشگاه را `paused` می‌کند؛ خطای شبکه با backoff نمایی تا ۱۰ بار تکرار می‌شود.
- آدرس sandbox در `config/services.php` (`MOADIAN_SANDBOX_URL`) قابل تغییر است.

فایل‌ها: `app/Services/Moadian/*`، `app/Models/Moadian*`، `MoadianController`، مسیرهای `api/accounting/moadian/*`، مایگریشن `2026_09_28_200000_create_moadian_tables` و `database/sql/create_moadian_tables_manual.sql`؛ فرانت: `/admin/accounting/moadian` (منوی حسابداری).

## نقطهٔ ادامه

1. اجرای مایگریشن (یا SQL دستی) روی سرور و اطمینان از اجرای `schedule:run` در cron.
2. گرفتن دسترسی sandbox (شناسهٔ حافظهٔ تستی)، ساخت کلید از صفحهٔ تنظیمات، ثبت کلید عمومی و گواهی، «آزمایش اتصال».
3. ارسال چند فروش آزمایشی و بررسی خطاهای برگشتی سامانه؛ تطبیق نام فیلدهای پاسخ استعلام در `MoadianApiV2Gateway` در صورت تفاوت.
4. تکمیل کدهای واحد اندازه‌گیری و شناسه‌های کالا، سپس رفتن به محیط اصلی.
5. در صورت انتخاب شرکت معتمد: پیاده‌سازی `MoadianTspGateway`.
