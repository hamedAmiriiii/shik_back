# اسناد فرانت — حسابداری (برنچ `coding`)

این فایل برای تیم فرانت است. بعد از هر مرحلهٔ بک‌اند همین‌جا به‌روز می‌شود.

| مرحله بک‌اند | وضعیت سند فرانت |
|---------------|------------------|
| ۱ کدینگ | نوشته شده |
| ۲ موتور سند | نوشته شده |
| ۳ فروش / خزانه | نوشته شده |
| ۴ خرید / تولید / برگشت | نوشته شده |
| ۵ گزارش دفتر | نوشته شده |
| ۶ پرمیشن و فعال‌سازی | نوشته شده |
| ۷ بستن سال | هنوز نه |
| ۸ تفصیلی طرف‌حساب | هنوز نه |
| ۹ ارزش افزوده | هنوز نه |

همهٔ روت‌ها زیر `/api` هستند و `Authorization: Bearer` می‌خواهند (گروه `auth:sanctum`).

اگر جدول هنوز روی دیتابیس نیست، APIها **۴۲۲** می‌دهند با `message` فارسی (migration/SQL اجرا نشده).

---

## وضعیت فعلی برای UI

**الان می‌توانید بسازید**
- صفحهٔ درخت حساب (کدینگ)
- ساخت معین/تفصیلی غیرسیستمی
- لیست اسناد + جزئیات سند + ثبت سند دستی + برگشت سند
- فیلتر لیست اسناد بر اساس `source_type`
- تراز آزمایشی، دفتر حساب، سود و زیان، ترازنامه
- دکمهٔ افتتاحیه (`POST /api/accounting/opening`) برای صاحب/کارمند با پرمیشن حسابداری
- منوی حسابداری با کلید پرمیشن `accounting`

**عمداً وصل نکنید**
- از صفحهٔ اسناد، سند فروش/فاکتور/هزینه را دستی برگشت نزنید (حذف همان مدرک در عملیات خودش storno می‌سازد)
- گزارش `GET /api/reports` و `GET /api/financial-report/monthly` را با اعداد دفتر عوض نکنید؛ هر دو مبنای تعهدی نزدیک‌اند ولی دو گزارش جدا می‌مانند

**چه چیزهایی عوض نشده**
- APIهای POS، سبد، سفارش، تطبیق روزانه و تنخواه همان‌اند؛ فیلد حسابداری به پاسخ فروش اضافه نشده
- فرانت لازم نیست موقع فروش یا تطبیق API سند صدا بزند؛ بک‌اند خودش ثبت می‌کند

صاحب فروشگاه به روت‌های `accounting/*` دسترسی دارد. کارمند فقط با تیک کلید `accounting` در `GET /api/shop-permissions`.

## مرحله ۱ — کدینگ

### نسبت به قبل
هیچ API قدیمی‌ای عوض نشده. بخش حسابداری از صفر اضافه شده.

### چیز جدید

#### `GET /api/accounting/accounts`

درخت حساب همین فروشگاه. بار اول بذر پیش‌فرض را هم می‌سازد.

Query:
- `include_inactive=1` — حساب‌های غیرفعال هم بیایند (پیش‌فرض: فقط فعال)

موفق ۲۰۰:

```json
{
  "data": [
    {
      "id": 1,
      "parent_id": null,
      "code": "1",
      "name": "دارایی‌ها",
      "level": "group",
      "level_label": "گروه",
      "nature": "debit",
      "nature_label": "بدهکار",
      "kind": "asset",
      "is_system": true,
      "linked_type": null,
      "linked_id": null,
      "is_active": true,
      "children": []
    }
  ]
}
```

`children` بازگشتی است؛ همان شکل گره.

| فیلد | مقادیر |
|------|--------|
| `level` | `group` گروه، `kol` کل، `moein` معین، `tafsili` تفصیلی |
| `nature` | `debit` بدهکار، `credit` بستانکار |
| `kind` | `asset` `liability` `equity` `revenue` `cogs` `expense` |
| `linked_type` | `shop_account` (حساب ۱/۲/تنخواه)، `till` (صندوق فروش)، یا `null` |
| `is_system` | `true` = بذر؛ از این API ویرایش/حذف نشود |

کدهای مهم برای UI (قفل‌شده):

| کد | معنی |
|----|------|
| `11101` | صندوق فروش (وجوه در راه) — `linked_type: till` |
| `11111` | حساب ۱ |
| `11112` | حساب ۲ |
| `11120` به‌بعد | تنخواه (اولین تنخواه معمولاً `11120`) |
| `411` | درآمد فروش |
| `511` | بهای تمام‌شده |
| `611` | هزینه جاری |

وقتی در پنل حساب فروشگاه یا تنخواه جدید می‌سازید (`POST /api/shop-accounts`)، بک‌اند خودش تفصیلی نقد می‌سازد. فرانت لازم نیست جدا صدا بزند. نام حساب فروشگاه که عوض شود، نام تفصیلی هم عوض می‌شود.

#### `POST /api/accounting/accounts` — ۲۰۱

فقط معین یا تفصیلی **غیرسیستمی**. ماهیت و نوع از والد کپی می‌شود.

Body:

```json
{
  "parent_id": 12,
  "code": "61102",
  "name": "هزینه حمل",
  "level": "moein"
}
```

قواعد:
- `level=moein` → والد باید `kol` باشد
- `level=tafsili` → والد باید `moein` باشد
- `code` در همان فروشگاه یکتا

پاسخ: `{ "message": "حساب ایجاد شد.", "data": { ...گره بدون children } }`

۴۲۲ نمونه: «معین باید زیر حساب کل ساخته شود.»

فقط با کاربر پرسنل متصل به فروشگاه (مثل ساخت تنخواه).

#### `PUT /api/accounting/accounts/{id}` — ۲۰۰

فقط حساب با `is_system=false`.

```json
{ "name": "هزینه حمل فروشگاه", "is_active": false }
```

حساب سیستمی → ۴۲۲: «حساب‌های سیستمی از این مسیر ویرایش نمی‌شوند.»

حذف سخت نداریم؛ غیرفعال کنید.

### پیشنهاد UI مرحله ۱
- درخت بازشو بر اساس `children`
- قفل ویرایش روی `is_system`
- برچسب کنار تفصیلی اگر `linked_type === 'shop_account'` (حساب نقد فروشگاه)
- دکمهٔ «حساب جدید» فقط روی کل (برای معین) یا معین (برای تفصیلی)

## مرحله ۲ — اسناد حسابداری

### نسبت به قبل
APIهای مرحله ۱ همان‌اند. فروش و گزارش مالی هنوز سند نمی‌سازند.

### چیز جدید

شکل مشترک یک سند (`data` در show/store/reverse و هر آیتم لیست):

```json
{
  "id": 10,
  "number": 1,
  "date": "1404-06-09",
  "description": "تست تراز",
  "source_type": "manual",
  "source_id": 1,
  "status": "posted",
  "status_label": "ثبت‌شده",
  "reverses_voucher_id": null,
  "debit_total": 100000,
  "credit_total": 100000,
  "lines": [
    {
      "id": 1,
      "account_id": 5,
      "account_code": "11101",
      "account_name": "صندوق فروش (وجوه در راه)",
      "debit": 100000,
      "credit": 0,
      "description": "صندوق فروش",
      "sort_order": 1
    }
  ]
}
```

`date` شمسی `Y-m-d` است.

| `status` | `status_label` | معنی برای UI |
|----------|----------------|---------------|
| `posted` و `reverses_voucher_id == null` | ثبت‌شده | سند اصلی؛ می‌شود برگشت زد |
| `posted` و `reverses_voucher_id` پر | برگشت | سند storno؛ برگشت دوباره نه |
| `reversed` | برگشت‌خورده | اصل باطل‌شده؛ دکمهٔ برگشت مخفی |

`source_type` سند دستی معمولاً `manual` است. از مرحله ۳ به بعد رویدادهای فروش و خزانه هم در لیست می‌آیند (جدول مرحله ۳).

#### `GET /api/accounting/vouchers`

صفحه‌بندی لاراول (`data`, `current_page`, `last_page`, `total`, `per_page`, …).

Query:
- `per_page` پیش‌فرض ۲۰، حداکثر ۱۰۰
- `page`
- `source_type` اختیاری
- `status` اختیاری (`posted` یا `reversed`)

هر عنصر `data` همان شکل سند با `lines` است.

#### `GET /api/accounting/vouchers/{id}`

```json
{ "data": { "...سند..." } }
```

اگر مال فروشگاه دیگر باشد: ۴۰۴ `{ "message": "یافت نشد" }`

#### `POST /api/accounting/vouchers` — ۲۰۱

ثبت سند دستی. حداقل دو آرتیکل. جمع بدهکار باید با جمع بستانکار برابر باشد (تلرانس ۰.۰۱). هر آرتیکل فقط بدهکار یا فقط بستانکار.

```json
{
  "date": "1404-06-09",
  "description": "سند آزمایشی",
  "source_type": "manual",
  "source_id": 1,
  "lines": [
    { "account_code": "11101", "debit": 100000, "credit": 0, "description": "صندوق" },
    { "account_code": "411", "debit": 0, "credit": 100000, "description": "فروش" }
  ]
}
```

- `date` شمسی یا میلادی؛ خالی = امروز تهران
- به‌جای `account_code` می‌توان `account_id` فرستاد
- `source_type` پیش‌فرض `manual`
- `source_id` اگر خالی باشد بک‌اند شماره می‌دهد
- ثبت دوباره با همان `source_type` + `source_id` سند جدید نمی‌سازد؛ همان سند قبلی را ۲۰۱ برمی‌گرداند

۴۲۲های مهم:
- «سند نامتوازن است. جمع بدهکار و بستانکار برابر نیست.»
- «هر آرتیکل باید دقیقاً بدهکار یا بستانکار باشد.»
- «سند باید حداقل دو آرتیکل داشته باشد.»

پاسخ: `{ "message": "سند ثبت شد.", "data": { ... } }`

در فرم UI قبل از ارسال جمع دو ستون را نشان بدهید و دکمه را تا تراز بودن قفل کنید.

#### `POST /api/accounting/vouchers/{id}/reverse` — ۲۰۰

سند معکوس می‌سازد (آرتیکل‌ها جابه‌جا). اصل `reversed` می‌شود.

```json
{
  "message": "سند برگشت خورد.",
  "data": { "...سند برگشت با reverses_voucher_id = id اصل..." }
}
```

اگر همان سند قبلاً برگشت خورده: همان سند برگشت را برمی‌گرداند (تکراری نمی‌سازد).

۴۲۲: «فقط سند ثبت‌شدهٔ غیربرگشتی را می‌توان برگشت زد.»

#### `POST /api/accounting/vouchers/self-test`

برای تیم، نه برای کاربر فروشگاه. سناریوی تست موتور را روی همان فروشگاه اجرا می‌کند (یک سند ۱۰۰٬۰۰۰ تومانی می‌سازد و برش می‌گرداند). در منوی مشتری نگذارید.

موفق ۲۰۰ `{ "ok": true, "message": "...", "data": { ... } }`  
اگر کنترل رد شود ۴۲۲ با `ok: false`.

### پیشنهاد UI مرحله ۲
- لیست: شماره، تاریخ شمسی، شرح، جمع بدهکار/بستانکار، وضعیت
- جزئیات: جدول آرتیکل (کد، نام، بدهکار، بستانکار)
- دکمهٔ برگشت فقط وقتی `status === 'posted' && reverses_voucher_id == null`
- سند برگشت را لینک به اصل (`reverses_voucher_id`)
- انتخاب حساب آرتیکل از درخت مرحله ۱ (معین یا تفصیلی)

## مرحله ۳ — فروش، وصول، خزانه

### نسبت به قبل
هیچ API جدیدی اضافه نشده. شکل سند همان مرحله ۲ است. فروش، وصول و خزانه **خودشان** سند می‌سازند؛ فرانت نباید `POST /api/accounting/vouchers` را برای این رویدادها صدا بزند.

گزارش‌ها و فرم POS عوض نشده‌اند.

### چیز جدید (فقط در دادهٔ اسناد)

بعد از یک فروش/وصول/تطبیق/تنخواه، در `GET /api/accounting/vouchers` ردیف جدید می‌بینید.

| `source_type` | `source_id` | کی ساخته می‌شود |
|---------------|-------------|------------------|
| `purchase` | `purchases.id` | فاکتور حضوری، سبد مشتری، سفارش سایت (وضعیت ارسال‌شده)، پای میز |
| `installment_pay` | `installments.id` | پرداخت قسط بعدی (قسط اول نقدی داخل همان سند فروش است) |
| `debt_settle` | `purchases.id` | تسویه نسیه |
| `cheque_clear` | `cheques.id` | وصول چک متصل به فروش |
| `recon_deposit` | ردیف واریز تطبیق روزانه | واریز تطبیق به حساب ۱/۲/تنخواه |
| `account_transfer` | `shop_account_transfers.id` | شارژ تنخواه |
| `opening` | همیشه `1` | افتتاحیه نقد (مرحله ۶) |

فیلتر: `GET /api/accounting/vouchers?source_type=purchase`

#### الگوی آرتیکل (برای نمایش، نه برای ساخت دستی)

فروش نقد+کارت+چک با تخفیف و اعتبار (نمونه):

| کد | بدهکار | بستانکار |
|----|--------:|--------:|
| `11101` صندوق فروش | نقد+کارت | |
| `11401` چک دریافتنی | مبلغ چک | |
| `412` تخفیفات | تخفیف | |
| `613` اعتبار وفاداری | اعتبار مصرف‌شده | |
| `411` درآمد فروش | | فروش ناخالص خطوط |
| `511` بهای تمام‌شده | بها | |
| `11301`/`11302`/`11303` موجودی | | بها |

نسیه/اقساط: به‌جای (یا علاوه بر) صندوق، `11201` دریافتنی. شرح سند اقساط: «اقساط — طلب کامل».

وصول قسط/قرض/چک فروش: فقط جابه‌جایی دارایی است — **درآمد `411` یا `431` دوباره نمی‌خورد**. چک فروش عملیاتی هنوز ممکن است ردیف `Income` بسازد؛ در دفتر درآمد تکراری نیست.

تطبیق روزانه: دِ تفصیلی همان حساب فروشگاه (`11111` / `11112` / تنخواه)، یِ `11101`.

شارژ تنخواه: دِ مقصد، یِ مبدأ — بدون درآمد/هزینه.

حذف فاکتور (`DELETE` فروش) سندهای مرتبط (`purchase` و وصول‌های همان فاکتور) را storno می‌کند. حذف شارژ تنخواه هم همین‌طور.

اگر جدول حسابداری روی دیتابیس نباشد، فروش مثل قبل ثبت می‌شود و سندی ساخته نمی‌شود. اگر جدول باشد و سند نامتوازن شود، فروش خطا می‌دهد (عمدی).

### پیشنهاد UI مرحله ۳
- در لیست اسناد برچسب `source_type` (فروش / وصول قسط / تسویه نسیه / وصول چک / تطبیق / تنخواه / دستی)
- لینک از سند `purchase` به فاکتور (`source_id`) اگر صفحهٔ فاکتور دارید
- دکمهٔ برگشت روی سند `purchase` را مخفی یا با هشدار قوی: «حذف فاکتور از POS؛ برگشت دستی دفتر و عملیات را از هم جدا می‌کند»
- POS و تطبیق روزانه را عوض نکنید

## مرحله ۴ — خرید، تولید، برگشت، حقوق

### نسبت به قبل
باز هم API جدید نیست. فاکتور خرید، هزینه، تولید، برگشت، حقوق، چک و سند دستی **خودشان** سند می‌سازند.

### `source_type`های جدید

| `source_type` | `source_id` | کی |
|---------------|-------------|-----|
| `invoice` | `invoices.id` | صدور/ویرایش فاکتور خرید |
| `expense` | `expenses.id` | هزینه جاری (`611`) یا سرمایه (`12101`) یا حقوق/مساعده (`612`) |
| `document_payment` | `document_payments.id` | تسویه نسیه فاکتور/هزینه — فقط بستن `21101`، درآمد ندارد |
| `production` | `productions.id` | تولید: د `11303` / ی `11302` |
| `purchase_return` | `purchase_item_returns.id` | برگشت خط فروش (اگر سند فروش هنوز posted باشد) |
| `income` | `cheques.id` | ثبت چک دریافتنی بدون فروش: د `11401` / ی `431` |
| `manual_trade` | `manual_trades.id` | خرید دستی د `611` / فروش دستی ی `431` از حساب فروشگاه |

وصول چک صادره همان `cheque_clear` است: د `21201` / ی تفصیلی حساب. وصول چک فروش همچنان `cheque_clear` بدون درآمد تکراری.

حقوق از مسیر هزینه می‌آید (`source_type=expense`) نه `payroll_payment`. عنوان «پرداخت حقوق» / «مساعده» به معین `612` می‌رود. دو سند جدا ساخته نمی‌شود.

اعتبار وفاداری روی فروش (`credit_source=loyalty_purchase`) سند هزینه دوم ندارد؛ مرحله ۳ همان `613` را زده. اعطای دستی اعتبار: د `613` / ی `11201`.

فاکتور با لات ماده: بدهکار `11302`؛ بدون لات: `11301`. ترکیبی نقد/چک/نسیه چند آرتیکل بستانکار دارد (`حساب` / `21201` / `21101`).

### پیشنهاد UI مرحله ۴
- در فیلتر اسناد مقادیر جدول بالا را اضافه کنید
- برگشت سند `invoice` / `expense` / `production` از UI نکنید؛ حذف همان مدرک در پنل عملیات کافی است
- فرم فاکتور و هزینه را عوض نکنید

## مرحله ۵ — گزارش دفتر کل

### نسبت به قبل
گزارش‌های قدیمی (`GET /api/reports` و `GET /api/financial-report/monthly`) عوض نشده‌اند. این چهار روت فقط از آرتیکل سند (`accounting_lines`) عدد می‌گیرند. اصل برگشت‌خورده (`status=reversed`) و سند storno هر دو در گردش هستند تا هم خنثی شوند.

تاریخ query شمسی `Y-m-d` است (مثل بقیهٔ گزارش‌ها). اگر خالی باشد یعنی از اول تاریخچه / تا امروز.

مشاهده با `shopAtelierId` (صاحب هم می‌بیند). کارمند نیاز به پرمیشن `accounting` دارد.

### `GET /api/accounting/trial-balance`

Query: `from`, `to`, `include_zero=1` (پیش‌فرض فقط حساب‌های دارای گردش).

سطح سطر: تفصیلی + معین بدون تفصیلی.

```json
{
  "data": {
    "from": "1404-06-01",
    "to": "1404-06-09",
```

## مرحله ۶ — پرمیشن، افتتاحیه، مبنای تعهدی POS

### نسبت به قبل
- در `GET /api/shop-permissions` کلید `accounting` آمده (برچسب: حسابداری). برای کارمند این تیک را بزنید وگرنه همهٔ `accounting/*` با ۴۰۳ رد می‌شود.
- گزارش ماهانه/داشبورد POS فروش اقساط و چک را روز فاکتور کامل می‌شمارد (مثل دفتر). وصول بعدی فقط نقد است، سود تکراری نیست.
- هزینهٔ `credit_source=loyalty_purchase` هنوز در لیست هزینه‌ها برای حسابرسی هست ولی از جمع سود/هزینهٔ گزارش مالی کنار می‌رود (همان `credit_used` در سود فروش مانده).

### `POST /api/accounting/opening` — ۲۰۱ یا ۲۰۰

یک‌بار برای هر فروشگاه. ماندهٔ عملیاتی حساب‌های فروشگاه/تنخواه را با دفتر مقایسه می‌کند و فقط **اختلاف** را سند می‌زند: دِ تفصیلی نقد / یِ `311` سرمایه (اگر حساب منفی باشد برعکس). صندوق `11101` معادل عملیاتی ندارد و در افتتاحیه نیست.

سیاست: **از امروز به بعد** — تاریخچهٔ فروش/خرید بازسازی نمی‌شود. رویدادهای بعدی خودشان سند می‌سازند.

Body اختیاری:

```json
{ "date": "1404-06-09" }
```

`date` شمسی `Y-m-d` است؛ خالی = امروز تهران.

موفق:

```json
{
  "ok": true,
  "already_posted": false,
  "message": "سند افتتاحیه ثبت شد.",
  "data": { "...سند با source_type=opening و source_id=1..." }
}
```

| وضعیت | معنی |
|--------|------|
| ۲۰۱ `already_posted: false` | سند جدید |
| ۲۰۰ `already_posted: true` | همان سند قبلی (تکراری ساخته نمی‌شود) |
| ۲۰۰ `data: null` | اختلاف نقد صفر بود؛ سندی لازم نبود |
| ۴۲۲ | جدول نیست یا حساب پرسنل فروشگاه نیست |

دکمه را یک‌بار بعد از فعال‌سازی حسابداری بگذارید. اگر `already_posted` بود غیرفعالش کنید. فیلتر: `GET /api/accounting/vouchers?source_type=opening`.

### پرمیشن

کلید: `accounting`  
پیشوند مسیر: `accounting` (همهٔ درخت، سند، گزارش دفتر، افتتاحیه).

صاحب فروشگاه همه کلیدها را دارد. ساخت سند دستی در MVP لازم نیست.

پشتیبان فروشگاه (`GET /api/shop-backup` و دانلود zip) حالا `accounting_accounts`، `accounting_vouchers` و `accounting_lines` را هم می‌گیرد. بازگردانی id سند را به فاکتور/هزینه/چک جدید همان فروشگاه وصل می‌کند. بکاپ قدیمی نسخه ۱ بدون دفتر هم باز می‌شود؛ درخت حساب بعد از restore دوباره بذر می‌شود.

### پیشنهاد UI مرحله ۶
- آیتم منو «حسابداری» با تیک کارمند
- دکمهٔ «ثبت افتتاحیه» با تأیید؛ بعد از موفقیت یا `already_posted` مخفی
- در سود و زیان همان `note` کوتاه را نشان بدهید (دیگر مرحله ۶ را وعده نمی‌دهد)

### تست دستی (فروشگاه خالی؛ روی فروشگاه زنده فروش ساختگی نزنید)

1. فروش نقد  
2. فروش نسیه + تسویه  
3. فروش چک + وصول  
4. فروش اقساط + یک قسط بعد  
5. برگشت یک خط  
6. فاکتور خرید ماده + تولید + فروش تولید  
7. هزینه جاری از تنخواه  
8. تطبیق روزانه  

بعد از همه تراز آزمایشی و معادله ترازنامه باید برقرار باشند. بک‌اند: `php artisan accounting:health-check {atelier_id}`

## خطاهای مشترک

| وضعیت | معنی |
|--------|------|
| ۴۰۱ | توکن نیست |
| ۴۰۴ | سند/حساب مال این فروشگاه نیست |
| ۴۲۲ `message` | اعتبارسنجی یا جدول ساخته نشده |
| ۴۰۳ | کارمند پرمیشن `accounting` ندارد |

ساخت حساب و ثبت/برگشت سند مثل تنخواه فقط با **حساب پرسنل متصل به فروشگاه** است (`staffShopAtelierId`). مشاهدهٔ درخت و لیست اسناد با `shopAtelierId` (صاحب هم می‌تواند ببیند).
